### Q-02. CSRF 토큰을 프론트가 받는 방법 — 해결

**답 (BE-B, 2026-10-03, BE-A 도 그대로 따름)**
- `GET /session` 응답 본문의 `csrfToken` 필드로 받는다. 변경 요청 헤더는 `X-CSRF-Token`.
- 로그인 성공 · 세션 갱신 때 발급, 세션이 바뀌면 토큰도 바뀐다. 서버는 토큰과 `Origin` 을 함께 검증.
- `403 CSRF_FAILED` → FE 가 `GET /session` 을 한 번 불러 새 토큰을 받고 원래 요청을 **1회만** 재시도. 그래도 실패하면 로그인 만료 · 보안 오류로 처리, 추가 자동 재시도 없음.
- 재시도는 원래 요청과 **같은 `Idempotency-Key` · 같은 본문** (BE-A 결정 28).
- `API_SPEC.md` 와 OpenAPI 에 반영 예정 (I-02 의 "CSRF 토큰" 보완 항목).

**FE 반영**: PG-1 API 클라이언트에 넣는다. 필드 이름은 OpenAPI 생성본에서 확인한다.

### Q-04. 수능운 "시험 종류" 값과 판매 마감 — 해결

**답 (2026-10-03, PD · BE-A 일치)**
- 1차는 **실제 대학수학능력시험만**. 모의고사 등은 넣지 않는다.
- 시험 종류는 사용자가 고르지 않는다. `examType: CSAT` (운세 종류 `fortuneType: SUNEUNG` 과 구분).

### Q-05. 운세별 결과 섹션 키 · 타입 — 부분 (10/10)

**답 (2026-10-03)**
- PD: 운세는 일반 5종(애정 · 종합 · 재물 · 궁합 · 신살) + 수능운. 공통 구조 **요약 → 소제목 + 내용(반복) → 부족한 기운 + 부적**. 특수 섹션: 궁합 점수, 재물운 시기별 흐름(`PERIOD_GUIDANCE` 재사용 가능), 수능운 교시별 · 도시락 · 준비물. 순서는 F-02. 선물 수신 결과도 같은 ReadingViewer. "소제목 + 내용" 이 `TEXT` 로 안 되면 새 타입.
- BE-B: PD 정의를 받아 `sectionKey` · `sectionType` · `displayOrder` 를 한 계약으로 OpenAPI enum 에 넣는다. 배열 순서가 기본 표시 순서. 알 수 없는 `sectionType` 은 화면 전체 오류 없이 미지원 섹션으로 처리 권장. 신살(F-03 미정)은 enum 에 먼저 넣지 않는다.

**FE 반영**: ReadingViewer 는 배열 순서대로 그리고, 알 수 없는 타입은 그 섹션만 건너뛰는 분기 + Sentry 경고로 한다 (VIEWER). 키 · 타입 목록은 OpenAPI 대기.

**결정 (팀, 2026-10-03)**: 신살은 일반 5종에 포함 (잠정). 다룰 범위 · 섹션(F-03) · 부적(T-01A)은 미정 — 준비 안 되면 판매 목록에서 빠진다 (BE-A 결정 32).

**답 (PD 추가, 2026-10-03) — 신살 구성 (F-03 · T-01A)**: 나에게 있는 살 알아보기 → 살 다스리기 (겁주지 않는 톤). 섹션: 요약(살 n개) → 살별 소제목 + 내용(좋은 면 포함) → 살 다스리는 법 → 부족한 기운 + 살 막이 부적. 12신살 12종 + 특수살 5종(홍염 · 백호 · 양인 · 괴강 · 귀문관)을 모두 계산하고 있는 살만 보여 준다. 문구 17종은 PD. 10/15 까지 안 되면 1차에서 신살만 뺀다. F-02 · F-03 · T-01A 반영 PR (`cc60ab3`).

**남은 일**: BE-B 의 OpenAPI enum (BE 수능운 구현 시작 전), 17종 계산 가능 여부 (BE-B), 신살 관심 항목(F-01) 유지 여부 (PD), 문구 (10/15).

**답 (BE-B, 2026-10-09)**: 요약 섹션 키 `SUMMARY`, 일반 운세 섹션은 모두 `TEXT`. 일반 5종 상세는 카테고리별 고정 필드(Q-35 1). 수능운 키 → 타입 매핑 `SUMMARY` · `EXAM_DAY` · `FOCUS` · `ANXIETY_MANAGEMENT` · `MISSING_ELEMENT` = `TEXT`, `EXAM_PERIODS` = `PERIOD_GUIDANCE`, `MEAL` = `FOOD_RECOMMENDATION`, `PREPARATION` = `CHECKLIST` — 서버는 `type` 을 주지 않고 `key` · `content` · `sourceFactKeys` 만 준다(OpenAPI `GeneratedSection`). 타입만 정해도 항목 구조가 없어 Q-37 로 넘긴다. **신살**: 17종 신살 계산은 엔진에 없다. 지금의 `SPECIAL_STARS` 는 17종 결정론 계산 결과가 아니어서 "신살 17종 계산" 이라고 표시하면 안 된다 — F-03(PD 확정: 17종 계산 · 있는 살만)과 부딪힌다.

**정해 줄 것 (PD · BE-B, 10/15)**: 1차에서 신살을 팔지(F-03 · Q-05 "10/15 까지 안 되면 신살만 뺀다"), 판다면 화면 · 상품 설명에서 무엇을 약속할지.

### Q-07. "구매 상태 30분 유지" 보관 위치 — 해결

**답 (BE-A 결정 1 · 2 · 15 · 22 · 23 · 29 · 36 · 38, 2026-10-03)**
- 서버: 견적은 발급 후 **30분** 유효, 그동안 가격 보장. 응답에 `quoteId` · `productCode` · `price.currency` · `price.amount` · `expiresAt`, 등껍질 견적은 `walletBalance` · `shortage` · `recommendedTopUp`(충전 상품 코드)도. 부족분 · 추천은 서버 계산.
- 견적 조회 **`GET /quotes/{quoteId}`** (로그인한 소유자만, 원본 이름 · 생년정보 없음). 만료면 `409 QUOTE_EXPIRED`.
- 견적 만료: 선택은 지우지 않고 새 견적을 받는다. 새 가격이 다르면 다시 보여 주고 구매 확인을 다시 받는다. 판매 종료 · 비활성이면 판매 불가 안내.
- FE: 화면 복원 정보(인물 **ID**, 운세, 옵션 등 최소 선택값)를 **`sessionStorage`** 에 둔다. 마지막 선택 변경 후 24시간, 읽을 때 만료 검증, 구매 성공 · 로그아웃 시 즉시 삭제. 같은 탭에서만 복원(다른 기기 복원 없음). 저장한 가격 · 잔액은 결제 근거가 아니다.
- 견적 하나는 성공한 구매 하나에만 연결. 잔액 부족으로 구매가 시작되지 않았으면 충전 후 같은 견적을 다시 쓸 수 있다. 최종 실패 · 환급 후 새 구매는 새 견적 · 새 키.

**FE 반영**: 브라우저 저장소 규칙에 "구매 선택 복원(`sessionStorage`)" 을 추가했다 (PURCHASE-RESTORE). 정확한 요청 · 응답 필드는 OpenAPI 대기 (BE-A 도 "후속 계약"). API_SPEC 반영은 Q-17.

### Q-38. 구매 결과 · 환급 확인 — 부분 (10/12, f · g 남음)

BE-A 점검(`backend/docs/PRE_PR_INTEGRATION_REVIEW_20261009.md` 1 · 3) · FE 전달(10/10)에서 FE 코드와 다른 곳이 나왔다.

- `READING_GENERATION_FAILED` 는 **보상(환급) 자체가 실패해도** 반환된다 (`GeneralReadingService` — 보상 실패는 suppressed). FE `generationFailureOfError` 는 이 code 를 받으면 `refunded: true` 로 만들어 "사용한 등껍질은 돌려드렸습니다" 를 보인다 → **오류 code 만으로 환급 완료를 표시하지 않게 FE 가 고친다** (BE-A "높음").
- 구매 응답(`PurchaseResponse`)에는 `refunded` 가 없고, 처리 중이면 `readingId` · `balance` 가 null 일 수 있다. FE `ReadingPurchaseResult` 는 둘 다 필수 · `refunded` 필드가 있다 → 진짜 adapter 때 null 을 0 · 완료로 바꾸지 않고, `FULFILLED` + `readingId` 가 있을 때만 결과로 이동한다.
- `READING_FULFILLMENT_UNAVAILABLE`(503): 의존성 미연결 경로에서 차감 전에 거절된다. 재시도는 같은 구매 의도의 같은 `Idempotency-Key` (BE-B · BE-A 같음). 다만 네트워크 오류 등 결과 불명을 "차감 없음" 으로 일반화하지 않는다 (BE-A).
- `PURCHASE_DEBIT_MISMATCH`(500): **답 엇갈림** — BE-B "역분개 완료 뒤 반환하므로 '돌려드렸어요' + 고객센터 안내 가능, 역분개 실패는 별도 운영 오류" / BE-A "정상 보상 호출 후 반환하지만 환급 확정(receipt) 계약은 B 와 보완 중, 오류 code 만으로 환급 단정 금지".
- 구매 상태 조회(`purchaseId` GET)와 ID 를 받기 전 응답 유실의 재조회 방법은 A · B 협의 · 구현 대기. BE-A 쪽 기준(사용자 선택, B · FE 공동 승인 전): 응답 유실 · 새로고침은 새 구매 대신 기존 구매 확인으로, 자동 복구 실패 · 한도 초과는 "처리 확인 중" + 문의 경로(환급 완료 약속 없음).

### Q-39. API_SPEC 문서가 코드 · OpenAPI 와 다른 곳 · 로컬 확인 조건 — 해결 (10/13)
