## 1. 팀 문서끼리 어긋난 곳

### Q-03. 본인용 가격 단위 "조각"

- `PENDING_DECISIONS.md` P-03 표와 `PRD.md` 5장 "본인용 가격" 표는 가격을 `30조각`, `45조각` 처럼 **조각** 으로 적었다.
- 같은 문서의 P-01 은 재화가 **등껍질** 1종(`TURTLE_SHELL`)뿐이라고 했고, API 명세 견적 응답도 `currency: "TURTLE_SHELL"` 이다.

**왜 문제인가**: 화면의 단위 표기가 갈린다. FE 는 서버가 준 `currency` 를 보고 "등껍질" 로 표시할 예정이다.

**정해 줄 것**: "조각" 이 등껍질의 오기인지. 오기라면 P-03 · PRD 표를 고친다.

**담당 · 필요한 날**: BE-A · PD · 10/10

## 2. 정의가 비어 FE 화면이 막히는 곳

### Q-01. 충전 화면 경로 · 프레임이 없음

- `FUNCTIONAL_SPEC.md` 7장: 충전 진입점은 "**지갑 화면** 또는 유료 구매의 잔액 부족 모달". 12장 마이페이지에 "등껍질 충전·사용 내역".
- 같은 문서 2장 라우트 표에는 지갑 · 충전 경로가 없다. Figma 와이어프레임에도 충전 상품 선택 · 잔액 부족 모달 · 충전 내역 프레임이 없다.
- FE 는 새 페이지를 라우트 표(`src/lib/screens.ts` ROUTES)에 있는 것만 만든다.

**왜 문제인가**: PG 심사는 실제 판매 사이트에서 **결제창이 열리는지** 를 본다. 지금 결제창을 여는 원화 결제는 충전(등껍질)과 선물 두 가지인데, 선물은 원화 가격이 미정(P-03A)이라 심사 경로는 충전이 된다. 충전 화면이 없으면 PG-3 을 시작할 수 없다.

**정해 줄 것**
1. 충전을 별도 화면으로 둘지(예: `/wallet`), 마이페이지 안 섹션 · 바텀시트로 둘지.
2. 라우트를 `FUNCTIONAL_SPEC.md` 2장 표에 추가한다 (FE 가 경로 이름을 제안할 수 있다).
3. 프레임은 PG 심사 전에는 필요 없다 (PG-FIRST — 스타일 없이 만든다). 잔액 부족 모달(P-06) · 충전 내역 · 탈퇴 전 유료 잔액 안내(A-08) 프레임은 Phase 4 전까지.

**담당 · 필요한 날**: PD (경로는 FE 제안 가능) · 10/7

### Q-02. CSRF 토큰을 프론트가 받는 방법

- `API_SPEC.md` 1장: 세션 기반 변경 요청에 `X-CSRF-Token` 헤더 필수. `COMMON_RESPONSE_AND_ERROR_CODES.md` 7장: `403 CSRF_FAILED` 면 "CSRF 갱신 또는 새로고침 후 명령 1회 재시도".
- 토큰을 어디서 받는지(응답 헤더 · 읽을 수 있는 쿠키 · `GET /session` 응답 · 별도 API)가 없다. `PENDING_DECISIONS.md` I-02 도 "보완 필요: CSRF 토큰" 으로 남아 있다.

**왜 문제인가**: 충전 주문 생성(`POST /top-up-orders`) · 승인(`POST .../confirm`) · 로그아웃(`POST /auth/logout`)이 모두 변경 요청이다. 방식이 없으면 PG-3 을 끝낼 수 없다.

**정해 줄 것**: 토큰 발급 위치 · 이름 · 갱신 시점, `CSRF_FAILED` 후 다시 받는 방법.

**담당 · 필요한 날**: BE-B · 10/7

### Q-04. 수능운 "시험 종류" 값과 판매 마감 규칙

- `PENDING_DECISIONS.md` F-01: 수능운 추가 입력은 "시험 종류, 시험일". 값 목록이 어디에도 없다.

- `COMMON_RESPONSE_AND_ERROR_CODES.md` 4.5 의 `EVENT_DATE_NOT_ALLOWED` 가 어떤 규칙으로 나는지도 이것에 달려 있다.

**정해 줄 것**: 시험 종류 enum 값, 시험일을 사용자가 고르는지 고정인지, 수능 외 시험의 규칙.

**담당 · 필요한 날**: PD · BE-B · 10/10

### Q-05. 운세별 결과 섹션 키 · 타입 전체 목록

- `PENDING_DECISIONS.md` F-02 (확정)는 운세별 결과 순서를 정했다.
- `API_SPEC.md` 8장 결과 응답은 섹션 예시 4개(`SUMMARY` · `PERIODS` · `MEAL` · `PREPARATION`)와 타입 4개(`TEXT` · `PERIOD_GUIDANCE` · `FOOD_RECOMMENDATION` · `CHECKLIST`)만 있다. 나머지 섹션 키(시험 당일 · 집중 포인트 · 긴장 관리 · 애정운 현재 흐름 …)와 타입 대응이 없다. 신살은 F-03 미정.

**왜 문제인가**: FE 는 결과 화면을 섹션 타입별로 그리는 ReadingViewer 하나로 수능 · 일반 5종 · 선물 수신에 쓴다 (VIEWER). 키 · 타입이 OpenAPI enum 에 있어야 화면 순서와 빈 섹션 처리를 정할 수 있다.

**정해 줄 것**: 운세별 섹션 키 · 타입 · 순서를 OpenAPI enum 으로. 새 타입이 필요하면 그 모양.

**담당 · 필요한 날**: BE-B · PD · 10/11 (BE 수능운 구현 10/11~10/17 시작 전)

### Q-06. 본인 구매에서 부적 종류를 고르는 시점 · 화면

### Q-07. "구매 상태 30분 유지" 의 보관 위치

- P-06 (확정): 충전 후 선택한 운세 · 인물 · 옵션을 복원하고, 구매 상태를 최소 30분 유지.
- `API_SPEC.md` 5장 견적 응답에 `expiresAt` 은 있지만 유효 시간이 정해져 있지 않고, 견적 ID 로 다시 불러오는 API 도 없다.
- 충전은 토스 결제창으로 다른 페이지에 갔다 돌아오므로 프론트 메모리 상태는 사라진다. FE 는 전역 상태를 선물 위저드에만 쓰기로 했다.

**정해 줄 것**: 견적 유효 시간(30분 이상인지)과 재조회 API 유무. 없으면 "프론트가 보관" 으로 명시 (그 경우 저장 위치 · 만료 판단을 FE 가 정해 다시 묻는다).

**담당 · 필요한 날**: BE-A · 10/10

### Q-08. 선물에서 운세별 추가 입력 · 보내는 사람 이름

선물은 모든 운세가 가능하다(핵심 전제). 구매자는 수신자 이름 · 전화번호, 수신자는 자기 생년월일시 · 성별만 넣는다(G-05). 운세별 추가 입력(F-01)을 누가 넣는지가 없다.

| 운세 | 추가 입력 (F-01) | 선물에서 누가 넣나 |
|---|---|---|
| 궁합 | 상대방 공통 정보 + 관계 | 정의 없음 |
| 수능운 | 시험 종류 + 시험일 | 정의 없음 (Q-04) |
| 일반 공통 | 선택형 관심 항목 (F-04) | 정의 없음 |

또 `API_SPEC.md` 10장 선물 주문에 `senderName` 이 있는데 `FUNCTIONAL_SPEC.md` 10장 위저드 단계에는 보내는 사람 이름 입력이 없다 (카카오 닉네임인지, 입력하는지).

**정해 줄 것**: 위 표의 "누가 넣나", `senderName` 의 출처. 궁합 선물이 어렵다면 1차 출시에서 뺄지.

**담당 · 필요한 날**: PD (흐름) · BE-A (API) · 10/15

### Q-09. 선물 화면 Figma 가 단건 · 알림톡 방식과 다름

- 팀 문서: 선물은 단건(n일 공개 없음), 옵션 `TALISMAN_ONLY` / `READING_WITH_TALISMAN`, 원화 결제, 서버가 수신자 휴대전화번호로 알림톡 발송(G-10). 위저드는 운세 유형 → 옵션 → 수신자 이름 · 전화번호 → 부적 → 편지 → 검토 · 결제 (`FUNCTIONAL_SPEC.md` 10장).
- Figma: 23 "응원할 날 · 상품 (1장 / n일)", 24 "D-day별 가격 옵션 · 첫 부적 도착일" 이 n일 상품 기준이다. 25 수신인 정보에 전화번호 입력이 없고, 29 완료 화면에 알림톡 발송 상태 · 실패 시 안내가 없다.

**정해 줄 것**: 23 · 24 를 운세 유형 · 옵션 선택으로 바꾸고, 25 에 전화번호(마스킹 · 동의 문구), 29 에 발송 상태 · 재발송 · 실패 안내(G-10)를 넣는다. 24 를 없앨지.

**담당 · 필요한 날**: PD · 10/15

### Q-10. 공유 랜딩 경로와 공유 범위

**정해 줄 것**: 공유 랜딩 경로를 라우트 표에 추가할지와 화면 구성(제목 · 이미지 · 서비스 CTA), G-11.

### Q-13. 선물 링크 OG 에 수신자 이름을 넣는지

- G-08: 메시지는 OG · 검색 결과에 미노출. `FUNCTIONAL_SPEC.md` 11장: 유효한 미사용 링크는 수신자 이름 · 보낸 사람 이름 · 상품 종류를 화면에 표시.
- 알림톡 링크도 카카오톡 미리보기(OG)가 뜬다. OG 제목 · 이미지에 수신자 이름을 넣어도 되는지는 정의가 없다 (생년정보 · 메시지는 금지가 확정).

**정해 줄 것**: OG 에 이름(수신자 · 보낸 사람)을 넣는지.

**담당 · 필요한 날**: PD · 10/18

---

### Q-14. 캐릭터 에셋의 서버 합성 입력 형식 (보류 중)

- T-02 · T-03 · T-04: 띠 기준 12지 캐릭터, 기본 몸체 · 포즈 템플릿 + 표정 · 소품 · 부적 조합, 원본 1080×1920 PNG. 합성은 BE-B (`BACKEND_ROLE_SPLIT.md` 5장).
- FE 가 그리는 캐릭터를 서버가 SVG(레이어 이름으로 색 치환)로 받는지, 부위별 PNG 로 받는지 정의가 없다.

**정해 줄 것**: 입력 형식(SVG / PNG), 캔버스 크기, 레이어 이름 규칙.

**담당 · 필요한 날**: BE-B · PG 심사 요청(10/14) 후 (PG-FIRST 로 캐릭터 작업 보류)

### Q-15. 손그림 프레임과 모서리 · 그림자 토큰 (보류 중)

- D-01: 카드 20px · 버튼 16px · chip 999px, "옅은 종이 카드 그림자"(수치 없음). D-03 · D-05: 손그림 SVG 프레임을 9-slice(`border-image`)로 재사용.
- CSS `border-image` 는 `border-radius` 를 테두리에 적용하지 않는다. 모서리 모양은 프레임 그림이 정한다. `box-shadow` 는 박스 사각형을 따라가 손그림 테두리와 어긋날 수 있다.

**정해 줄 것**: 모서리 토큰의 용도(프레임 그림의 반경 지침인지, 프레임 없는 요소용인지), 그림자 수치 또는 "그림자 없음".

**담당 · 필요한 날**: PD · PG 심사 요청(10/14) 후, 에셋 확정(10/15) 전

## 3. 일정 · 운영 위험

### R-01. PG 심사에 올릴 상품과 충전형 재화 가맹

- P-02 충전 상품 6종 가격이 확정됐다 (2026-10-03). 선물 원화 가격(P-03A)은 미정.
- 토스페이먼츠 심사는 판매 예정 상품 1개 이상과, 비실물 상품의 제공기간 · 환불정책을 본다. 심사 중에는 상품 카테고리 · 판매 상태를 바꾸면 반려된다.
- P-08 외부 확인: "운세 · 부적 · **충전형 재화** 가맹점 승인".

**정해 줄 것**: 심사 상품을 충전(등껍질)으로 할지, 상품 카테고리 · 제공기간 문구, 충전형 재화가 가맹 승인 대상인지(토스 상담 결과).

**담당 · 필요한 날**: BE-A · PD · 10/10

### R-02. 캐릭터 출시 범위

- T-03 (확정): 12지 전체 출시. 캐릭터는 FE 가 혼자 그린다. 포즈 · 표정 · 소품 조합 수에 따라 작업량이 몇 배로 갈린다.

**정해 줄 것**: 출시 때 동물별 필요한 포즈 · 표정 · 소품 수, 우선순위.

**담당 · 필요한 날**: PD · 10/15 (캐릭터 작업은 PG 심사 요청 후 재개)

**정해 줄 것**: iPhone 을 빌려 줄 사람, 확인 날짜.

**담당 · 필요한 날**: 전원 · 10/24 (1차 교차 QA) — 결제창 확인은 PG 심사 전에 한 번 있으면 좋다

### R-04. 카카오 디벨로퍼스 설정

- 로그인(A-01)은 BE 가 OAuth 를 처리한다(`GET /auth/kakao/authorize` · `callback`). 리다이렉트 URI(스테이징 · 운영)가 등록돼야 PG-2 를 실기기로 확인할 수 있다.
- 공유(G-11)는 FE 가 Kakao JavaScript SDK 를 쓴다. JavaScript 키와 웹 도메인(스테이징 · 운영 · `boyeon` 미리보기 주소) 등록이 필요하다.

**정해 줄 것**: 앱 소유자, 리다이렉트 URI · 도메인 등록 시점, FE 에 JavaScript 키 전달.

**담당 · 필요한 날**: BE-B · 10/8 (리다이렉트 URI), 공유 키는 Phase 4 전

### R-05. 카드사 심사용 테스트 계정

- 토스페이먼츠 안내: 회원만 살 수 있는 사이트는 심사 담당자에게 테스트 계정(ID/PW)을 줘야 한다. 우리는 충전 · 구매가 카카오 로그인 필수(A-02)이고 로그인은 카카오만(A-01).

**정해 줄 것**: (a) 심사 전용 카카오 계정을 만들어 전달 / (b) 심사 상품만 비로그인 구매 허용 — (b) 는 확정 결정 A-02 를 바꾸는 일이다.

**담당 · 필요한 날**: PD · BE-A · 10/12 (카드사 심사 요청 전)
