# FE 전달: 환불 화면 및 연결 작업

기준: 2026-10-13, main의 PR #27 병합 완료 (`bb3169c`). FE 전달용 구현 요청이며 정책의 대외 확정본은 아니다. 이 문서 작성에서 FE 코드는 변경하지 않았다.

## 1. 결론

환불은 **고객센터 문의 접수 → 운영자 확인 → 관리자 API 실행**으로 진행한다.

- 사용자용 환불 신청 버튼·신청 폼·즉시 환불 화면은 만들지 않는다.
- 별도 관리자 웹 화면도 이번 FE 작업에 포함하지 않는다. 운영자는 Postman 등 관리 도구를 사용할 수 있다.
- FE에는 환불정책, 고객센터 안내, 본인 충전 주문의 환불 상태·실제 환불액 표시가 필요하다.
- 새 페이지를 반드시 만들 필요는 없다. 지갑/마이페이지의 충전 내역과 주문 상세에 연결하는 구성을 권장한다. 현재 내역 UI가 없다면 목록과 간단한 상세를 추가한다.

## 2. 표시할 정책

- 고객이 신청한 충전 건의 현재 유효한 잔여 유료 등껍질 전체를 한 번에 환불한다.
- 실제 결제액 × 남은 유료 등껍질 ÷ 처음 지급한 유료 등껍질로 계산한다. 원 미만 올림, 별도 수수료 없음.
- 미사용이면 전액, 일부 사용하거나 7일이 지나도 잔여 유료분을 환불할 수 있다.
- 남은 보너스는 회수한다. 이미 사용한 보너스는 현금 환불하지 않으며 환불액에서 공제하지 않는다.
- 신청 없이 자동으로 현금 환불하지 않는다. 접수만으로 환불 완료가 되는 것도 아니다.
- 만료된 유료분·서비스 종료·미성년자 등 예외는 일반 처리와 구분한다. 대외 문구는 PD/사업 검토 후 확정한다.
- 금액은 서버 값만 표시한다. FE가 잔액으로 환불액을 계산하거나 회수량을 결정하지 않는다.

정책 원본: `docs/policies/REFUND.md`.

## 3. 필요한 화면

### A. 환불정책 페이지 `/refund` — 필수

현재는 제목과 빈 시행일·목차·본문 영역만 있다. 최종 원고를 받아 본문·시행일·고객센터 신청 방법을 채운다.

- 수수료 없음, 잔여 유료분 비례 환불, 보너스 처리 방식을 설명한다.
- 고객센터 링크와 처리 기한은 담당자 확정값을 사용한다. 임의 이메일·기한을 넣지 않는다.
- 초안을 법률 검토가 완료된 확정본으로 표시하지 않는다.

### B. 고객센터 안내 — 필수

지갑 또는 마이페이지에서 문의 경로를 찾을 수 있게 한다. 별도 문의 시스템 구축은 필수가 아니다.

- 실제 채널이 확정되면 링크/이메일 등을 연결한다.
- 환불 문의 시 주문번호, 결제 일시, 결제 금액을 확인하도록 안내한다.
- 주문 상세에서 주문번호를 확인하거나 복사할 수 있게 한다.
- 비밀번호, 세션 쿠키, 토스 시크릿 키 등을 요청하거나 수집하지 않는다.

### C. 충전 내역·주문 상세의 상태 표시 — 연결 필요

표시 정보: 결제 일시, 원 결제 금액, 주문번호, 주문 상태. 환불 기록이 있으면 실제 환불액과 완료 시각을 추가한다.

권장 배치:

```text
지갑 / 마이페이지
  충전 내역
    결제 일시 · 원 결제 금액 · 현재 상태
  주문 상세
    주문번호 · 원 결제 금액
    환불 상태 · 실제 환불액 · 완료 시각
    고객센터 문의
```

회수 유료/보너스 수량은 관리자 API에만 있는 값이다. 사용자 refund GET에는 없으므로 해당 수량을 표시하려고 관리자 API를 호출하거나 잔액으로 추정하지 않는다.

## 4. FE API·타입 변경

### 사용 API

| API | 용도 |
|---|---|
| `GET /api/v1/top-up-orders` | 본인 충전 내역 조회 |
| `GET /api/v1/top-up-orders/{orderId}` | 주문 상태 조회 |
| `GET /api/v1/top-up-orders/{orderId}/refund` | 본인 주문의 환불 기록·실제 금액·완료 시각 조회 |
| `GET /api/v1/wallet` | 최신 잔액 재조회 |

공통 응답의 `data` 안에 업무 응답이 있다. 로그인 세션이 필요하며 타인 주문 조회는 허용하지 않는다.

환불 GET 주요 필드: `refundId`, `orderId`, `state`, `amount`, `nextAction`, `completedAt`.

고객센터 접수만 있고 금융 실행 전이면 환불 기록이 아직 없을 수 있다. 소유자 주문에 환불 기록이 없을 때도 GET은 404다. 이 응답을 '접수 안 됨' 또는 '환불 거절'로 단정하지 않는다. 사용자에게 고객센터 접수 상태를 직접 보여 주는 API는 이번 범위에 없다.

### 제거·동기화할 것

1. 이전 `POST /api/v1/top-up-orders/{orderId}/refund`는 제거됐다. FE의 `requestRefund()` 연결·포트·가짜 구현·관련 테스트를 정리하고 호출하지 않는다. `getRefund()`는 유지한다.
2. 공유 `docs/openapi/api-v1.json`은 이전 사용자 POST와 상태 계약을 포함한다. 최신 서버 계약으로 export하고 FE 생성 타입을 **같은 FE PR에서** 갱신한다. 기존 공유 경로를 보존하며 백엔드 전용 파일을 그대로 덮어쓰지 않는다.
3. `pnpm api:types`로 `frontend/src/types/api.d.ts`를 갱신한다. 최신 환불 계약 근거는 `backend/docs/openapi/payment-operations-v1.json`이다.
4. 주문 상태 포트·adapter·화면 분기에 `PARTIALLY_REFUNDED`를 추가한다. 현재 `REFUND_PENDING` 지원은 유지한다. 알 수 없는 상태를 완료로 바꾸지 않는다.
5. 환불 조회·상태 표시는 연결하되 `/api/v1/admin/**`는 일반 사용자 FE에서 사용하지 않는다. 관리자 권한이나 시크릿 키를 FE에 넣지 않는다.

## 5. 화면 상태 분기

### 주문 상태

| 주문 status | 표시 기준 |
|---|---|
| `CREDITED` | 충전 지급 완료. 환불 완료를 뜻하지 않는다. |
| `REFUND_PENDING` | 환불 처리 중 또는 확인 필요. `nextAction`과 환불 GET을 함께 확인한다. |
| `REFUNDED` | 원 결제액 전체 환불 상태. 상세 금액·완료 시각은 환불 GET으로 확인한다. |
| `PARTIALLY_REFUNDED` | 원 결제액보다 적은 현금 환불 완료 상태. 상세는 환불 GET으로 확인한다. |
| 미지의 값 | 완료 안내 없이 상태 확인/문의 경로 제공. |

`PARTIALLY_REFUNDED`도 해당 주문의 정상 잔여분 환불 작업은 끝난 상태다. '추가 환불 신청' 버튼을 제공하지 않는다.

### 환불 기록 state

| refund state | 표시/행동 |
|---|---|
| `RESERVED`, `IN_FLIGHT`, `RETRY` | 처리 중. 같은 주문을 재조회하며 완료 안내를 하지 않는다. |
| `REFUNDED` + 유효한 `completedAt` | 환불 완료. 실제 환불액은 **refund.amount**를 표시한다. |
| `REVIEW_REQUIRED` | 확인 필요. 자동 재시도나 새 신청 대신 고객센터 안내. |
| `REJECTED` | 환불 미완료. 고객센터 안내. |
| 미지의 값·조회 실패 | 결과 확인 불가. 재조회/문의, 완료로 추정하지 않는다. |

- refund의 `state=REFUNDED`는 해당 요청 금액 완료다. 무조건 원 결제액 전부 환불된 뜻이 아니다.
- 원 주문의 `amount`는 원 결제액으로 유지된다. 이를 실제 환불액으로 표시하지 않는다.
- HTTP 200, 지갑 잔액 감소, 사용자 결제창 복귀만으로 완료라고 표시하지 않는다.
- 운세 구매의 `REFUNDED`는 등껍질 반환이며 현금 환불과 구분한다.
- 현재 잔액은 지갑 API로 다시 읽는다. 주문 응답의 지급 당시 잔액이나 FE 자체 차감으로 맞추지 않는다.

표시 문구 후보: '환불 처리 중', '환불 내역 확인이 필요해요', '환불 완료', '환불되지 않았어요. 고객센터로 문의해 주세요'. 화면에 넣을 최종 문구는 PD 확인을 받는다. 입금 시각이나 카드 취소 반영 기한을 임의로 약속하지 않는다.

## 6. 오류 안내

- `WALLET_REVIEW_REQUIRED` (409): 지갑 확인 필요. 같은 충전/구매를 반복하도록 안내하지 않고 고객센터로 연결한다. 충전 주문 생성·운세 구매 차감 등에서도 발생한다.
- `REFUND_NOT_ELIGIBLE` (409): 관리자 실행 등에서 발생할 수 있다. 일반 사용자 FE는 환불 실행 API를 호출하지 않는다.
- 401: 로그인 안내. 네트워크 실패·503: 완료로 추정하지 않고 기존 주문 확인 경로를 유지한다.
- 상세 기준: `docs/COMMON_RESPONSE_AND_ERROR_CODES.md`.

## 7. 테스트 요청

FE 단위·계약 테스트:

- 제거된 사용자 환불 POST를 호출하지 않는지.
- `PARTIALLY_REFUNDED`를 UNKNOWN으로 낮추지 않는지.
- 원 결제액과 다른 refund.amount가 실제 환불액으로 표시되는지.
- 처리 중·검토·반려·조회 실패·미지의 상태에서 완료 화면이 나오지 않는지.
- 완료 시각 누락은 완료로 표시하지 않는지.
- 환불 GET 404를 접수 거절로 오해하지 않는지.
- 공유 OpenAPI·생성 타입 동기화, lint/typecheck 및 관련 테스트.

팀 통합 테스트는 분리 스테이징이 준비되면 후속으로 진행한다:

- 로그인 → 충전 → 일부 사용 → 고객센터 신청 → 관리자 실행 → FE 실제 환불액/상태·잔액 확인.
- 미사용 전액, 보너스만 사용, 유료 일부 사용 사례 확인.
- 새로고침·조회 실패 후에도 허위 완료 표시가 없는지 확인.
- 중복 실행·PG 결과 불명·원장 대조는 A가 검증한다. FE는 직접 토스 취소하거나 임의 paymentKey로 테스트하지 않는다.

## 8. 담당과 남은 제공값

| 담당 | 할 일 |
|---|---|
| FE | 계약/생성 타입/포트·adapter 정리, 정책·문의 안내, 주문 내역/환불 상태 표시, 화면 테스트 |
| A | 서버 환불 처리·중복 방지·원장/PG 복구, 운영자 API 사용 안내, 금융 결과 검증 |
| B·A·FE | 고정 스테이징 주소, 로그인·프록시·키 짝·상품/기능 활성화와 팀 연결 검증 |
| PD·사업 | 최종 정책 원고·시행일·화면 문구·고객센터 채널·처리 기한·사업자 정보 |

현재 BE 일반 환불 기능은 병합됐지만 기본 비활성이며 실제 PG·FE 통합 검증 완료를 뜻하지 않는다. 실서비스 키 지원·가상계좌·법정 예외 등은 별도 범위다.

BE 상세 문서: `backend/docs/CUSTOMER_CENTER_REFUNDS_20261013.md`.
