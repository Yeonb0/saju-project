# PD 환불 초안·현재 구현·운영 방식 검토

확인일: 2026-10-13 (한국 시각). GitHub main `6716045`와 미병합 draft PR #27 `5ea03ef`를 확인했다. 현재 브랜치의 금융 로직은 main과 같고 PR의 코드 차이는 오류 표시 문구다. 이번 작업은 코드·기존 테스트 원문 검토와 공식 자료/서비스 공개 정책 조사다. 테스트 재실행이나 실제 PG·FE 결제/환불 검증은 하지 않았다.

## 1. 결론과 이번 사용자 선택

등껍질 충전 구조를 유지한다면, 잔여 유료분 환불을 지원하도록 초안과 구현을 함께 맞추는 것을 추천한다. 구현 전에 초안의 금액·보너스·접수 기준을 먼저 확정한다. 콘텐츠 1건에 직접 결제하는 서비스와 여러 콘텐츠를 구매하는 충전 재화 서비스의 환불 범위는 다르다. 서비스 규모가 작다는 이유만으로 두 구조의 정책을 동일하게 취급하지 않는다.

- 사용자는 잔여 유료분 환불 허용과 별도 수수료 없는 비례 정산을 선택했다. 이전 10-12 부분 환불 미제공 결정은 대체한다.
- 계산의 기본: 해당 충전 건의 실제 결제액 × 해당 건의 남은 유료 등껍질 ÷ 처음 지급한 유료 등껍질. 보너스 수량은 유료 수량의 분모에 넣지 않는다. 보너스 사용분 공제 여부는 아직 미정이다.
- 예: 5,000원으로 유료 500개를 지급받고 유료 100개를 사용했다면 기본 환불액은 4,000원이다. 보너스 정산·원 단위 반올림 등은 최종 결정이 필요하다.
- 7일 이내 전부 미사용 전액 취소와 그 이후/일부 사용의 잔여분 환불을 구분한다. 전자는 기존 기능을 재사용하고 후자는 추가 구현한다.
- 현금 환불은 고객센터 신청에 따라 처리한다. 구매 실패 시 등껍질 반환과 신청 후 미완료 환불 복구는 계속 별도다.

## 2. main·PR·초안 구분

## 4. 운영상 중요한 공백

### 접수 시각과 실행 시각

고객이 6일째 이메일로 신청했는데 운영자가 8일째 기존 API를 실행하면 기한을 넘겼다고 거절될 수 있다. 접수 원본/시각과 서버 등록 시각을 각각 기록하고, 운영자 입력 시각의 출처·변경 감사 및 접수 후 사용 방지 방식을 정해야 한다. 모든 과거 날짜를 운영자가 자유롭게 입력해 기한을 우회하는 방식은 피한다. 법정 기산점과 철회 의사표시의 효력은 아래 법령을 함께 검토한다.

### 회사 오류와 보상 이력

현재 `WalletOperationsService.reclaimUnusedTopUp`는 해당 지급분에 과거 음수 원장 한 건이라도 있으면 거절한다. 구매 실패 후 등껍질이 전부 돌아온 경우도 그렇고 `CashRefundOperationsTest.spentCreditAndCompensatedUsageCannotAutomaticallyCashRefund`에 명시돼 있다. 잔여분 환불 계산에서는 단순 과거 사용 이력 대신 유효한 원장/반환 후 잔여량을 정산해야 한다. 회사 귀책 문의까지 일반 미사용 gate만으로 거절하지 않도록 예외 경로를 마련한다.

### DB·PG 경계

현재는 주문/지갑을 잠그는 짧은 DB 처리에서 회수 원장과 환불 의도를 함께 저장한 뒤 잠금을 풀고 토스에 취소를 요청한다. 확인된 전액 취소 증거가 있어야 환불과 주문을 완료 상태로 저장한다. 같은 요청은 기존 환불을 재사용하고 결과 불명은 같은 취소 의도로 조회/재시도하며, 횟수 초과는 검토 상태로 남긴다. 새 잔여분 환불도 이 경계를 유지하면서 요청별 취소액·회수량·누적 환불액을 영속 저장해야 한다. 결과 불명에서 새 요청으로 다시 취소하거나 잔액을 임의 반환하지 않는다.

## 6. 법령·토스 확인이 필요한 이유

전자상거래법 제17조는 청약철회의 기산점을 계약내용 서면/공급 시점으로 정하며, 서면 철회 의사표시의 발송 시점, 디지털콘텐츠 제공 개시의 제한, 가분적 콘텐츠의 미제공 부분, 사전 안내/시험 제공 조치 등을 규정한다. 주문 생성 후 168시간을 모든 경우에 적용하거나 일부 사용만으로 모든 잔액을 배제해도 되는지는 등껍질의 거래 구조에 맞춰 확인해야 한다. 이는 최종 법률 판단이 아니다. [현행 제17조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031805921)

표시·광고와 다르거나 계약과 다르게 이행한 경우의 철회는 일반 7일/미사용과 다른 기간을 둔다. 회사 귀책·법정 취소 권리를 단순변심 환불 규칙과 분리해 초안에 적는다. [제17조 제3항](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1022341977)

적법한 청약철회 등의 환급은 법 제18조의 적용 시점과 3영업일 기준, 결제업자에게 지체 없이 취소 요청할 의무를 함께 검토해야 한다. 임의로 긴 검토 기간을 정하고 카드사 반영 지연과 회사 처리 기한을 합쳐 쓰지 않는다. [제18조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000527285)

토스 취소 API는 취소액을 받아 부분 취소를 지원하지만 결제수단마다 기한/제약이 다르다. 가상계좌 환불에는 환급 계좌도 필요하다. API 지원이 환불 정책 결정이나 판매 구조의 계약 승인을 뜻하지 않는다. [토스 취소 API](https://docs.tosspayments.com/reference#결제-취소), [결제수단 정책](https://docs.tosspayments.com/guides/v2/get-started/payment-methods)

## 7. 고객센터와 관리 기능 권고

고객센터는 신청을 받는 창구, 관리자 기능은 내부 주문·지갑을 확인하고 환불을 실행하는 수단이다. 작은 서비스에서도 역할을 나누는 것은 적절하며 같은 운영자 한 명이 두 역할을 맡을 수 있다. 별도 고객센터 프로그램이나 큰 관리자 웹사이트를 만들 필요는 없다.

1. 이메일 또는 카카오 채널 한 곳으로 접수하고 주문 ID·접수 시각·신청자·사유를 기록한다. 원 주문 소유자 대조 절차를 정한다.
2. 지정 운영자가 관리자 API로 환불 대상 주문/유료 잔량/기본 환불액/보너스 회수량을 확인한다.
3. 사유·접수 증거·요청키를 갖춘 관리자 명령으로 서버 계산 금액만 실행한다. 금액 자유 입력이나 임의 잔액 수정은 1차 범위에 넣지 않는다.
4. PG와 내부 주문·원장 결과를 함께 확인하고 처리 중/완료/검토 상태를 구분해 고객에게 답한다.

초기 기술 담당자는 Postman 등으로 관리 API를 사용할 수 있다. 비개발자가 반복 처리하게 되면 주문 검색·환불 확인·실행·결과 조회 정도의 작은 내부 화면을 추가하는 편이 실수를 줄인다. 이번에는 FE 코드를 수정하지 않는다. 토스 상점관리자에서만 취소하면 내부 재화 회수와 경쟁할 수 있으므로 정상 절차는 내부 서버를 거친다. 이미 외부 취소가 발생했다면 기존 대사/검토 경로로 처리한다.

## 8. 후속 구현·검증

- 먼저 결정: 사용 보너스 공제 여부, 원 단위 처리, 충전 건별/잔액 전체 신청, 만료분과 종료 예외, 7일 기산점, 실제 채널·처리 기한.
- BE-A: 접수/운영자 명령·환불액 산정·잔여 유료/보너스 회수·PG 부분 취소 검증·누적 환불/명령 중복·결과 불명 복구·감사.
- B/FE/PD 공동: 실제 구매 실패 반환과 환불, 탈퇴 제약, 콘텐츠 최초 제공 근거, 안내/동의/정책 원고.
- PostgreSQL 검사: 같은/다른 요청키 중복, 구매와 환불 동시성, 두 주문 혼합 잔액·할인·보너스·반올림, 중단/timeout, PG 성공 후 DB 실패, 늦은 응답, 외부 취소, 만료/보상 후 정산, 권한 철회와 감사 저장 실패.
- 실제 분리 환경: 지원 결제수단별 부분 취소·재조회와 고객센터→운영자→내부 재화/PG 결과 대조. 자동 테스트 통과와 실제 PG 검증을 구분한다.
