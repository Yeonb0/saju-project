# BE-A 정책 검토 및 팀 전달

작성일: 2026-10-13

PD 약관 3종과 FE 10/13 확인 요청(Q-42~Q-49)을 검토한 A파트 전달사항입니다. 확정 방향과 제안·추가 확인을 구분합니다. 아래의 ‘수정 방향’은 구현 완료를 뜻하지 않습니다. 법률 검토·실제 PG·운영 설정 확인을 대신하는 문서도 아닙니다.

## 1. PD에게 전달할 내용

### 1-1. 충전 환불은 자동이 아니라 신청 기반입니다

환불정책 4조 및 PD 팀 전달 문서의 ‘자동 전액 환불’, ‘BE-A 구현 그대로’ 표현은 수정이 필요합니다. 현재 구현은 신청 없는 자동 현금 환불이 아닙니다.

권장 문구:

> 충전 후 7일 이내에 해당 충전으로 받은 유료 등껍질과 보너스 등껍질을 모두 사용하지 않았다면, 고객센터 이메일로 신청하여 결제 금액 전액을 환불받을 수 있습니다. 함께 지급된 보너스 등껍질은 회수하며, 환불은 원래 결제 수단으로 처리합니다.

- 미사용 전액 환불과 잔여 유료분 환불 모두 고객센터 이메일로 접수합니다.
- 잔여 유료분은 수수료 없이 환불하며, 같은 충전에서 받은 남은 보너스만 회수합니다. 사용한 보너스는 현금으로 공제하거나 추가 청구하지 않습니다.
- 현재 등록 상품은 유료 1개당 100원이므로 기존 비례 계산과 환불액이 같습니다. 서버는 실제 결제액에 비례해 계산합니다. 할인 상품을 추가하면 ‘항상 100원/개’ 정책과 함께 재검토해야 합니다.
- 여기서 말하는 미사용은 해당 주문의 유료·보너스 지급분 기준입니다. 계정 전체 잔액으로 판단하지 않습니다.
- 구매 생성 실패에 대한 등껍질 자동 보상은 충전 현금 환불과 별개입니다.

Q-42 답변: FE가 제안한 1번(문구 수정)을 채택합니다. 셀프 환불 POST·버튼이나 신청 없는 자동 현금 환불은 추가하지 않습니다.

PAY-01 안내 문구 제안:

> 충전 후 7일 이내, 해당 충전의 유료·보너스 등껍질을 모두 사용하지 않았다면 고객센터로 신청해 전액 환불받을 수 있어요.

### 1-2. 개인정보는 목적별로 필요한 기간만 보관합니다

개인정보 저장을 최소화하고 불필요해진 정보는 삭제하는 방향으로 정했습니다. 다만 정확한 항목별 종료 시점은 삭제 구현과 함께 맞춰야 합니다.

| 정보 | 권장 정리 방향 |
|---|---|
| 선물 수신 전화번호 | 사용자 확정: 구매 후 30일 미만에 알림톡 재발송·알림톡을 통한 링크 재발급 지원, 기간 종료 후 삭제 |
| 수신자 생년정보 | 운세 생성·재열람에 필요한 최소 범위와 기간만 보관 |
| 선물 메시지 | 콘텐츠에 포함된다면 열람 기간에 맞춰 별도 보관 |
| 발송용 원문 token | 발송 작업 종료 후 제거, 검증용 hash와 필요한 작업 기록만 유지 |
| 결제·환불 기록 | 법정 보관 대상과 필요한 금융 증거를 일반 개인정보와 분리해 보관 |

- 전화번호 보관과 콘텐츠 재열람 기한을 같은 기준으로 묶지 않습니다.
- 30일은 사용자 확정이며 A 코드에 경계를 반영했습니다. 구매 후 30일이 지나도 이미 받은 유효 링크의 콘텐츠 열람은 유지하지만 알림톡 재발송·재발급은 종료됩니다. 링크 분실 시 알림톡으로 다시 받을 수 없다는 안내가 필요합니다. 삭제 worker는 기본 비활성이고 실제 운영 활성화·대행사/백업 삭제 검증은 별도입니다.
- ‘구매 후 90일 내 최초 제공’과 ‘최초 제공 후 90일 재열람’을 구분해 적어 주세요. 링크 접속 자체와 완성된 콘텐츠 최초 제공도 구분해야 합니다.
- 현재 구현의 만료 후 24시간 유예·보관기간 조건은 확정본의 ‘전화번호 최대 90일’과 다릅니다. 정확한 삭제 시점을 맞추기 전 두 조건이 일치한다고 안내하지 않습니다.
- 탈퇴 후 불필요한 개인정보를 일괄 30일 보관하는 방식은 재검토합니다. 금융·분쟁 증거를 제외한 불필요한 개인정보는 신속히 정리하는 방향입니다.
- 현재 유료 잔액이 있으면 탈퇴가 제한되므로 ‘유료 잔액 환불 후 탈퇴 가능’ 안내도 실제 서버 동작과 맞춰 주세요.

### 1-3. 결제 결과 불명에는 미청구를 단정하지 않습니다

서버의 결제 상태 조회·중복 방지·복구 구조는 유지하고, 상태별 문구를 수정합니다.

| 상황 | 문구 방향 |
|---|---|
| 결제 승인 전 확정된 사용자 취소·미결제 | 취소 안내. 미청구 문구는 실제 미결제가 확인된 경우에만 사용 |
| 확정 실패 | 실패 안내. 서버가 재결제를 허용하는 상태일 때만 다시 결제하기 제공 |
| 승인 응답 유실·결과 불명·지급 처리 중 | ‘결제 결과를 확인하고 있어요. 다시 결제하지 말고 잠시 후 확인해 주세요.’ |
| 검토 필요 | ‘확인이 필요한 결제예요. 고객센터로 문의해 주세요.’ |

‘모든 실패는 등껍질 미지급·금액 미청구’라는 일괄 문구는 사용하지 않습니다. 환불 완료도 접수나 취소 호출만으로 표시하지 않습니다.

### 1-4. 미성년자 결제는 허용하고 충전 한도를 추가하지 않습니다

사용자 결정: 미성년자 결제를 일괄 차단하지 않으며, 별도 충전 한도는 도입하지 않습니다. 현재 만 14세 미만 가입 제한과 만 14~18세의 유료 계약 문제는 별개입니다.

결제 전 안내 문구 제안:

> 미성년자는 법정대리인의 동의를 받아 결제해 주세요. 법정대리인의 동의 없이 체결한 계약은 미성년자 본인 또는 법정대리인이 취소할 수 있습니다.

- 이 안내는 결제 전에 쉽게 확인할 수 있게 표시하고 환불정책의 미성년자 조항과 맞춥니다.
- 안내 표시만으로 법정대리인의 실제 동의를 받았거나 확인했다고 간주하지 않습니다. 카카오 로그인·PG 인증·이용자 본인 체크도 그 자체로 보호자 동의를 입증하지 않습니다.
- 모든 결제에 별도 보호자 SMS 인증이 법적으로 의무라고 단정하지는 않습니다. 신규 인증 기능의 도입은 이번 문서에서 확정하지 않으며, PG 계약상 조건과 구체적 동의 확인 방식은 출시 전 확인사항으로 남깁니다.
- 법정대리인이 범위를 정해 처분을 허락한 재산 등 예외가 있으나, 소액이라는 이유만으로 모든 거래가 예외라고 판단하지 않습니다.
- 동의 없는 미성년자 계약 취소 요청은 일반 ‘7일·미사용’ 자격만으로 거절하지 않습니다. 이미 사용·열람한 거래도 사실관계와 법정 예외를 별도로 검토해야 합니다. 현재 일반 잔여분 환불 API가 이 예외를 모두 처리하는 것은 아닙니다.

근거: [민법 제5·6조](https://www.law.go.kr/lsInfoP.do?ancYnChk=0&lsId=001706), [전자상거래법 제13조 제3항](https://www.law.go.kr/LSW/LsiJoLinkP.do?docType=JO&joNo=003100000&languageType=KO&lsNm=%EC%A0%84%EC%9E%90%EC%83%81%EA%B1%B0%EB%9E%98+%EB%93%B1%EC%97%90%EC%84%9C%EC%9D%98+%EC%86%8C%EB%B9%84%EC%9E%90%EB%B3%B4%ED%98%B8%EC%97%90+%EA%B4%80%ED%95%9C+%EB%B2%95%EB%A5%A0&paras=1). 법률 적합성의 최종 판단을 대신하지 않습니다.

### 1-6. 추가 문구·운영 확인

- 고객센터 신청 후 3영업일 처리·이메일 안내는 운영 담당자가 지킬 절차가 필요합니다. 서버의 자동 이메일·영업일 관리가 구현돼 있다는 의미는 아닙니다.
- 정상 제공 후 단순 변심에 따른 환불 제한과, 미제공·계약과 다른 제공·미성년자 결제 등 예외는 구분합니다. ‘어떤 경우에도 환불 불가’처럼 표현하지 않습니다.
- 외부 서비스 장애의 포괄적 면책, 디지털 콘텐츠 청약철회 제한 고지·미리보기 등은 출시 전 법률 검토가 필요합니다.
- 약관 시행일은 심사 요청일에 자동으로 맞추지 말고 실제 게시·적용 일정과 맞춥니다.
- 가입 동의·14세 확인·분석 제외·공급자 보관 설정은 팀회의 안건으로 남깁니다. 미구현 기능을 이미 시행 중인 것처럼 확정적으로 게시하지 않습니다.

## 2. 팀 전체에게 전달할 내용

### 2-1. A파트 처리 구조

**고객센터 이메일 접수 → 운영자 본인·주문 확인 → 관리자 API로 환불 가능 금액 확인 → 실행 → PG 결과·원장 확인 → 결과 이메일 안내**를 유지합니다.

- 사용자용 환불 신청 폼·즉시 환불 화면은 1차에 추가하지 않습니다.
- 별도 관리자 웹 화면은 필수가 아닙니다. 권한 있는 운영자가 Postman 등으로 기존 관리자 API를 사용합니다. 고객 계정 대리 로그인이나 DB 직접 수정으로 처리하지 않습니다.
- 환불 회수·기록·중복 방지와 결과 불명 복구는 기존 서버 구조를 유지합니다. 접수만으로 완료하거나, 응답이 끊겼다고 새 환불을 실행하지 않습니다.
- 일반 관리자 경로는 해당 충전의 현재 유효한 잔여 유료분 전체를 정산합니다. 법정 예외·서비스 종료 등 특수 사유는 일반 자격 조건으로 일괄 거절하지 말고 별도 검토합니다.

### 2-2. FE 연결 요청

- 환불정책과 고객센터 이메일 안내, 충전 주문·환불 상태 조회를 연결합니다. 환불 금액은 서버 값만 표시합니다.
- 문의 접수와 서버의 `REFUND_PENDING`은 다릅니다. 금융 처리를 시작하기 전 이메일만 접수된 상태를 API가 보여 주지는 않습니다.
- 결과 불명에는 같은 주문 재조회·고객센터 안내를 사용하고, 자동으로 새 주문·재결제로 이동하지 않습니다.
- 선물 구매 ACTIVE, 알림톡 SENT, 콘텐츠 최초 제공은 서로 다릅니다. 발송 202는 예약이지 전달 완료가 아닙니다.

문의 식별번호 제안(Q-47):

| 문의 유형 | 메일 제목 |
|---|---|
| 충전 | [뿌기사주 문의] 충전 주문번호 {orderId} |
| 운세 구매 번호 있음 | [뿌기사주 문의] 운세 구매번호 {purchaseId} |

현재 A 관리자 API는 충전 주문 목록·환불 목록·사용자 지갑 원장·환불 케이스를 제공합니다. 추가한 `GET /api/v1/admin/top-up-orders/{orderId}`는 충전 주문을 정확한 ID로 조회하며 DB 관리자 권한·감사 기록을 요구하고 결제 비밀값은 반환하지 않습니다. 충전 환불 케이스 등록에는 orderId와 확인된 customerUserId가 필요합니다. purchaseId/quoteId로 운세 구매를 직접 찾는 관리자 검색 API·화면은 없습니다. 목록의 after는 검색 조건이 아니라 페이지 cursor입니다. 본인 확인과 운세 구매 조회 경로는 별도 보완사항입니다.

환불 상태 표시(Q-48):

- REFUND_PENDING: ‘환불 처리 중’. 접수 완료만으로 이 태그를 붙이지 않습니다.
- PARTIALLY_REFUNDED: 완료된 잔여 유료분 환불로서 실제 환불액 표시. ‘환불 처리 중’이나 결제 결과 불명과 같은 상태로 취급하지 않습니다.
- REFUNDED: 환불 증거와 내부 기록이 확정된 완료 상태.
- REVIEW_REQUIRED: 확인 필요·고객센터 안내. 완료라고 단정하지 않습니다.
- 충전 성공/결과 화면에서도 결제 완료·환불 처리 중·환불 완료를 구분합니다. 1차 내역 화면 제외는 아직 확정하지 않았으며, 제외 시 환불 진행 안내를 이메일과 기존 주문 조회에서 어떻게 제공할지 함께 결정합니다.

FE 요청서가 ‘맞음’으로 표시한 실패 문구도 결과 불명까지 미청구로 단정하면 안 됩니다. 1-3의 상태별 문구 정정을 우선합니다. 시행일은 ‘심사 요청일’ 자체가 아니라 실제 게시·적용 일정과 맞춥니다.
