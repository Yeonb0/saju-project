# 백엔드 A 상세 골격

## 범위와 현재 상태

2026-10-09 최신: 견적/지갑 조회 HTTP API와 지갑 차감·원장·원거래 복구 DB adapter가 있다.
지갑 쓰기는 기본 비활성이며 실제 구매 복구 worker·충전/PG·인증/인물 연결은 후속이다.
상세 활성화 경계와 검증 범위는 `WALLET_PURCHASE_IMPLEMENTATION.md`를 따른다.
아래 파일 배치와 순수 함수 설명은 초기 골격 기록이며 최신 구현 상태와 구분한다.
미구현 인터페이스에는 성공을 가장하는 임시 구현을 두지 않고 인증/CSRF를 유지한다.

## 파일 배치

| 경로 (`src/main/java/com/sajuppugi/` 기준) | 들어 있는 것 | 다음 구현 |
|---|---|---|
| `catalog/domain` | 가격/통화, 판매 기간, 상품 스냅샷, 30분 견적 | 확정 상품 seed, 견적 선택 항목 정규화 |
| `catalog/application`, `catalog/port` | 상품·견적 조회/발급, 견적 구매 연결 계약 | 소유권 확인, 현재 판매 가능 여부 재검사, 견적 단건 구매 제한 |
| `wallet/domain` | 잔액, lot, 차감 정렬, 불변 원장/배분 검증 | 실제 차감·보상 계산, lot 만료 처리 |
| `wallet/application`, `wallet/port` | B 호출용 차감/보상, 잔액/내역 조회, 잠금 저장 계약 | DB 잠금, lot·원장·잔액 원자적 갱신 |
| `payment/domain` | 원화 충전 주문과 지급량 스냅샷 | 승인/지급 상태 전이 구현 |
| `payment/application`, `payment/port` | 충전 생성/승인/조회, PG 승인/조회/취소 계약 | 토스 adapter, 금액 검증, 지급 중복 방지, 대사 |
| `gift/domain` | 미사용/사용 만료, 최초 접근 유예, 전달 재시도/수동 제한 | 선물 상태·제공물 연결과 만료 job |
| `gift/application`, `gift/port` | B 호출용 접근 확인, 전달/재발급, token hash 교체 계약 | 안전한 토큰 생성, 검증/폐기, 선물 주문 서비스 |
| `common/idempotency` | 요청 키, 원자적 점유/응답 재사용 계약 | DB unique 제약, 처리 중/본문 불일치 오류 매핑 |
| `common/outbox` | 업무 변경과 동일 트랜잭션으로 작업 등록하는 계약 | 암호화, worker 잠금/재시도, 민감 payload 삭제 |
| `admin/application` | 감사 기록 계약 | 관리자 조회·조작 서비스와 권한 검증 |

이 목록은 완성 API DTO가 아니다. 메서드 입력의 사용자 ID는 인증된 서버 문맥에서 가져온다.
현재 `UUID`를 내부 경계에 사용하며 상대 모듈의 entity/repository를 노출하지 않는다.
개별 계약의 DB 구현은 트랜잭션 및 동시성 테스트를 함께 작성해야 한다.

## 코드로 반영한 확정 규칙

- `CatalogService`와 `JdbcCatalogRepository`는 활성·판매 기간 내 상품을 조회하고 30분 견적을 저장한다. 견적에는 상품 가격·버전·판매 설정의 스냅샷을 저장한다.
- 견적은 본인만 조회하며 타인/미존재는 같은 404, 본인 만료 견적은 `QUOTE_EXPIRED`다. 구매 연결 저장은 조건부 UPDATE로 한 번만 수행한다. 실제 구매 시 판매 상태·권한·만료 검사는 후속 구매 서비스에서 다시 수행해야 한다.
- 현재 견적은 최소 단일 상품 도메인 계약의 저장 구현이다. 제공물·할인 전 가격·다건 선물 견적·HTTP DTO는 아직 추가하지 않았다. 사용자 테이블 연결 FK는 B의 테이블 구현 후 후속 migration으로 추가한다.
- 충전 상품은 최신 팀 문서 기준 6종을 등록하고 `availableTopUps`로 가격·유료/보너스/총 지급량을 조회한다. PG·지급 준비 전에는 모두 비활성 상태이며, 이 등록으로 실제 충전·지급을 시작하지 않는다. 본인 운세·선물 seed와 제공물·할인 전 가격은 아직 없다.
- `QuoteFundingService`는 본인 운세/추가 부적의 소유자·만료 검증된 견적에 최신 사용 가능 잔액과 부족분을 붙인다. 활성·판매 기간 내 충전 상품의 보너스 포함 지급량으로 부족분을 채울 수 있는 최소 원화 가격 상품 코드를 추천한다. 조회는 차감이나 견적 소비를 하지 않는다.
- 추천할 단일 상품이 없거나 충전 판매가 비활성이면 `recommendedTopUp`은 null이며 부족분은 그대로 반환한다. 최대 상품 초과 시 조합 추천 정책은 결정하지 않았다. 선물 견적의 지갑 계약·다건 계산도 이 기능에 포함하지 않는다.
- `WalletQueryService`는 지급분에서 현재 사용 가능한 유료/보너스 잔액을 계산한다. 만료·미래 지급분을 제외하며 조회만으로 지갑을 만들거나 잔액을 변경하지 않는다. 저장된 잔액 projection과의 대사·소멸 원장 생성은 후속 작업이다.
- 지갑 내역은 소유자별 최신 시각/ID 순서의 cursor pagination이다. 최대 100건, 잘못된/타인/미존재 cursor는 `INVALID_CURSOR`다. 현재 내부 계약에는 거래 유형 필터·HTTP DTO가 없다.
- DB에도 거래 방향·0 금액·자기 역분개·중복 배분을 제한하고, 배분의 거래와 지급분은 같은 지갑 소유자여야 한다. 배분 합계·중복 환급·잔액 갱신은 후속 쓰기 서비스에서 트랜잭션으로 검증해야 한다.

- 견적은 발급 시 상품/가격 스냅샷을 보관하고 정확히 30분에 만료한다. 구매 때 현재 판매 가능 여부도 확인해야 한다.
- 판매 시작은 포함, 종료는 제외한다. KST 판매 종료일은 서비스에서 다음 날 00:00을 종료 시각으로 변환한다.
- lot은 만료 임박 순, 같은 만료 시 보너스 우선, 이후 지급 시각과 ID 순으로 정렬한다. 만료/빈/future lot은 제외한다.
- `WalletDebitPolicy.allocateDebit`는 이 순서로 요청량을 나눠 음수 원장 배분을 계산한다. 부족 잔액·중복 lot·0 이하 요청을 거절하고 입력 잔액을 변경하지 않는다. DB 차감·구매·잔액 갱신은 아직 수행하지 않는다.
- 원장 배분은 중복 lot 없이 거래 총액/부호와 일치해야 한다. 수정 대신 역분개 거래를 추가한다.
- 원장 거래 방향은 `TOP_UP` 양수, `PURCHASE`/`EXPIRY` 음수다. `REFUND`는 구매 복구(양수)와 현금 환불에 따른 회수(음수), `ADJUSTMENT`는 증가/감소를 모두 허용하되 0은 금지한다. 세부 배분도 총액과 같은 방향이어야 한다.
- 거래가 자기 자신을 역분개 대상으로 참조할 수 없다. 원거래의 실제 존재/소유자/복구 가능액/중복 복구 검사는 후속 서비스·DB 구현에서 수행한다. 현재 타입 검증만으로 환불이나 복구를 승인하지 않는다.
- 선물 미사용 기한은 승인부터 90일. 기한 전 정상 입력을 마친 경우 최초 제공은 미사용 기한 +24시간 미만까지 가능하다.
- 사용 기한은 최초 콘텐츠 응답 성공부터 90일이다. 토큰 재발급으로 연장하지 않는다.
- 알림톡은 최초 발송 + 최대 3회 재시도. 확인된 일시 오류에만 직전 실패부터 1/5/30분 뒤 재시도한다. 결과 불명은 조회로 확인한다.
- 수동 재발송/링크 재발급은 합산 KST 일 3회, 최소 1분 간격이다. 수락된 실패도 횟수에 포함한다. 자동 재시도는 제외한다.
- `manualAvailability`의 `acceptedToday`는 저장소가 KST 당일 기준으로 계산해야 한다. 진행 중·소유권·선물 만료·취소 검증과 횟수 예약은 서비스/DB에서 원자적으로 수행한다.
- 결제 결과 불명은 실패로 단정하지 않는다. 충전은 승인만으로 완료되지 않고 원장 지급까지 커밋된 `CREDITED`가 완료다.

## B와 맞출 내부 계약

- `WalletPurchasePort.debit`: 사용자/견적/내부 멱등 키 → 원장 거래 ID, 차감량, 커밋 시점 잔액. 2026-10-09 DB adapter 추가, 기본 비활성. 재전송은 최초 잔액 snapshot을 반환하므로 현재 잔액은 별도 조회한다.
- `WalletPurchasePort.compensate`: 최초 거래 ID/사유/내부 멱등 키 → 원거래 배분에 대한 한 번의 보상 거래. DB adapter 추가; 실제 구매 복구 worker는 후속이다. 상세: `WALLET_PURCHASE_IMPLEMENTATION.md`.
- `GiftAccessPort`: token 및 부적 대상을 확인하고 gift ID/접근 만료를 반환한다. 입력 검증·사주·결과·부적 생성은 B에서 제공한다.
- 기존 역할 문서의 예시와 달리 현재 타입은 `UUID`를 사용하고 보상도 멱등 키를 받는다. B 연동 전에 양쪽이 서명을 확인한다.

외부 enum은 임의 변경하지 않는다. 내부 `Product.Category.READING`은 API `FORTUNE`,
원장 `PURCHASE`/`EXPIRY`는 API `SPEND`/`EXPIRATION`으로 HTTP adapter에서 매핑한다.
지금은 adapter가 없어 내부 enum이 HTTP로 노출되지 않는다.

## 아직 넣지 않은 것

- 선물 가격/결제 통화, 환불 산식/보너스 회수, 궁합 선물 출시, 알림톡 대행사: 기본값 없이 미정 유지.
- 선물 주문 생성/승인과 환불의 상세 DTO·상태 전이는 위 정책과 최종 API 계약을 맞춘 뒤 구현한다.
- 상품 실데이터, 실제 수능 날짜, PG 계정/키, 알림톡 템플릿은 등록하지 않는다.
- 멱등 기록 보존 기간, 관리자 세부 권한, job 주기/잠금/재처리 운영 정책은 이번 골격으로 확정하지 않는다.
- 원문 token/전화번호/편지/결제 키를 로그에 남기지 않는다. outbox는 암호화 payload만 받으며 실제 암호화·보관 기간·로그 마스킹은 별도 구현한다.

## 권장 구현 순서

1. B와 사용자 FK/공개 port/HTTP DTO를 확인하고 상품·견적 DB 및 서비스를 구현한다.
2. 지갑/lot/원장 migration, 잠금 차감/보상, 동시성·멱등 테스트를 구현한다.
3. 충전 주문/토스 test adapter/원자적 지급/결과 불명 대사를 구현한다.
4. 선물 토큰/접근 상태/outbox/전달 worker를 구현하고 B의 제공물 port를 연결한다.
5. 미정 정책 확정 뒤 선물 구매·환불을 완성하고 관리자 권한/감사·운영 job을 연결한다.

## 검증

`BackendAPolicyTest`는 위 순수 정책의 경계값, 금액/원장 검증과 민감값 `toString` 마스킹을 검사한다.
기존 통합 테스트는 공통 응답·보안·health 동작을 검사한다.
DB 동시성, 실제 PG/알림톡, token 폐기 경쟁, 환불은 아직 검증 대상 구현이 없다.
상품·견적 및 지갑 조회 통합 테스트는 테스트 DB에서 실제 migration과 SQL을 실행한다. PostgreSQL 검증은 README의 `TEST_DATABASE_*` 환경변수 또는 GitHub CI를 사용한다.

```powershell
.\gradlew.bat --no-daemon clean check bootJar
```
