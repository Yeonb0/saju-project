# A/B 구매 연결 합의 요청

2026-10-11 갱신: B 회신의 책임 분리/구매 조회 DTO/복구 원칙을 A 측에서 수용했다.
최신 확정·보완·남은 작업은 [회신 반영 기록](TEAM_CONTRACT_DECISIONS_20261011.md)을 따른다.
아래 내용은 최초 협의 요청의 기록이다. receipt 읽기 포트 보완 서명은 B 재확인 대상이며 구현 완료가 아니다.

전달 기준: 2026-10-10, BE-A PR #17 main 병합 완료(`f47b719`).
이 문서 하나로 구매 연결 협의를 요청할 수 있다. 현재 A 구현은 PR #17/OpenAPI를 참고한다.

## B에게 요청하는 회신

1. 구매 상태 조회 API와 생성 재개는 B, 지갑 원장/receipt는 A가 맡는 제안에 동의하는지.
2. 상태 GET 및 purchaseId 수신 전 응답 유실 시 기존 구매를 찾는 방법과 응답 DTO.
3. CREATED/DEBITED/GENERATING의 중단 재개, 중복 생성/늦은 결과 차단 설계.
4. 환급 receipt 검증과 REFUNDED 전이, 복구 실패/한도 초과 처리의 담당 경계.
5. 위 계약을 FE에 전달할 수 있는 시점과 실제 세션/인물 연결의 준비 상태.

합의가 필요한 항목에 대해 동의/수정안을 회신해 달라는 요청이며,
이 문서 자체가 B에게 일방적으로 확정된 구현 지시나 완료 보고는 아니다.

## 현재 구현 경계

A는 지갑 지급분/원장/잔액/영속 receipt와 FAILED 구매 보상 재처리를 구현했다.
B는 구매 상태와 생성 결과를 관리한다. 같은 DB라도 A 차감과 B 상태 저장은 별도 커밋이다.
HTTP 요청 키에 다른 본문을 보내는 것은 차단하지만 최초 응답 replay와 생성 재개는 아직 없다.
구매/복구는 기본 비활성이며 이 문서는 합의안이지 확정된 계약이 아니다.

## 사용자 선택: A 측 사용자 흐름 기준 (2026-10-10)

사용자가 아래 두 추천 방향을 선택했다. A 측 인계 기준으로 기록하며,
B/FE/PD의 공동 승인이나 API 구현 완료를 의미하지 않는다.

1. 생성 중 응답 유실/새로고침/재접속은 새 구매를 바로 만들지 않고 기존 구매 확인으로 복귀한다.
   동일 구매 의도의 키/quote/선택을 유지하며, 시간 초과만으로 실패·환급을 단정하지 않는다.
2. 자동 복구가 실패하거나 재시도 한도에 도달하면 환급 완료를 약속하지 않고
   '처리 확인 중' 안내와 문의 경로를 제공한다. 원장/구매 상태 확인 후 결과를 확정한다.

확정하지 않은 것: 정확한 화면 문구와 CS 연락처/처리 기한, 조회 간격·횟수,
API 응답 필드, 생성 lease/fencing·재개 구현, 관리자 처리 담당과 알림 방식.
기존 purchaseId를 받기 전에 응답이 유실된 경우에도 확인할 수 있도록,
B와 동일 키/quote에서 기존 구매 ID를 찾는 계약을 합의해야 한다.
구매 기록 재조회에 생년정보 원문/세션 토큰을 브라우저 저장소에 추가하지 않는다.

구현 후 검증할 항목:
- 차감/구매 저장 후 HTTP 응답을 잃거나 새로고침해도 기존 구매로 복귀하고 추가 차감이 없는가.
- 조회 실패나 시간 초과에 새 구매/새 키가 자동 생성되지 않는가.
- 복구 실패/한도 초과에서 환급 완료 문구가 없고, 문의에 연결할 구매 ID가 제공되는가.
- 뒤늦게 복구가 성공하면 서버의 확정 상태로 화면이 갱신되며 환급 원장은 한 건인가.

## 1. 소유자 구매 상태 조회

- 제안: B가 `GET /api/v1/reading-purchases/{purchaseId}`를 제공하고 A는 지갑 receipt 확인을 지원한다.
- 상태, purchaseId, 완료 때만 readingId, 환급 확인 여부의 응답 형식과 FE polling/종료 조건을 함께 정한다.
- 미완료 readingId/잔액은 null을 허용하고 null을 0이나 성공으로 바꾸지 않는다.
- 타인/없는 구매는 같은 404, 본인 인증은 실제 세션 principal UUID를 사용한다.
- 견적 만료 후에도 이미 완료된 본인 구매를 조회할 수 있어야 한다. 최초 구매의 만료 검사와 완료 조회를 분리한다.

## 2. 서버 중단과 생성 재개

- CREATED인데 A 차감 receipt가 이미 있는 경우, B 상태 저장 전 중단일 수 있다.
- DEBITED/GENERATING은 생성 작업 소유자, lease 만료, 재시도 한도, 늦은 결과 저장 차단 기준이 필요하다.
- 제안: B가 생성 상태/lease/fencing을 책임지고 A는 이미 커밋된 차감/복구 receipt를 재사용한다.
- 단순 시간 초과만으로 환급하지 않는다. 늦게 완료된 생성이 환급 후 제공되지 않도록 B의 완료 조건과 A 보상 조건을 합의한다.
- 기존 FAILED 재처리만으로 위 상태의 중단 복구가 완료되지는 않는다.

## 3. 환급 완료 판정

- 생성 오류 code는 환급 성공 증거가 아니다. FE는 오류만으로 완료 문구를 표시하지 않는다.
- B 즉시 보상은 A receipt의 사용자/견적/원거래/복구 거래를 검증한 뒤 REFUNDED로 전이해야 한다.
- A 복구 원장은 저장됐지만 B 상태 갱신이 실패한 경우, 같은 역분개를 재사용해 상태만 다시 맞춘다.
- 복구 실패/재시도 한도 초과의 사용자 표시, 관리자 처리 담당과 운영 알림을 정한다.

## B 합의 없이 진행하는 A 작업

충전 주문 생성/소유자 조회, 서버 가격·지급량 snapshot, 주문 키 중복 방지,
이후 토스 승인/결과 불명 조회와 지갑 지급 트랜잭션은 A 결제 모듈에서 진행한다.
이 작업은 B의 구매/생성 상태 머신을 변경하지 않는다.
정책 동의/보관 기간/판매 활성화와 실결제는 별도 확정·검증 대상이다.
