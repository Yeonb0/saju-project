# A/B 구매 연결 합의 요청

## 현재 구현 경계

A는 지갑 지급분/원장/잔액/영속 receipt와 FAILED 구매 보상 재처리를 구현했다.
B는 구매 상태와 생성 결과를 관리한다. 같은 DB라도 A 차감과 B 상태 저장은 별도 커밋이다.
HTTP 요청 키에 다른 본문을 보내는 것은 차단하지만 최초 응답 replay와 생성 재개는 아직 없다.
구매/복구는 기본 비활성이며 이 문서는 합의안이지 확정된 계약이 아니다.

## 1. 소유자 구매 상태 조회

- 제안: B가 `GET /api/v1/reading-purchases/{purchaseId}`를 제공하고 A는 지갑 receipt 확인을 지원한다.
- 상태, purchaseId, 완료 때만 readingId, 환급 확인 여부의 응답 형식과 FE polling/종료 조건을 함께 정한다.
- 미완료 readingId/잔액은 null을 허용하고 null을 0이나 성공으로 바꾸지 않는다.
- 타인/없는 구매는 같은 404, 본인 인증은 실제 세션 principal UUID를 사용한다.
- 견적 만료 후에도 이미 완료된 본인 구매를 조회할 수 있어야 한다. 최초 구매의 만료 검사와 완료 조회를 분리한다.

## 2. 서버 중단과 생성 재개

- CREATED인데 A 차감 receipt가 이미 있는 경우, B 상태 저장 전 중단일 수 있다.
- DEBITED/GENERATING은 생성 작업 소유자, lease 만료, 재시도 한도, 늦은 결과 저장 차단 기준이 필요하다.
- 제안: B가 생성 상태/lease/fencing을 책임지고 A는 이미 커밋된 차감/복구 receipt를 재사용한다.
- 단순 시간 초과만으로 환급하지 않는다. 늦게 완료된 생성이 환급 후 제공되지 않도록 B의 완료 조건과 A 보상 조건을 합의한다.
- 기존 FAILED 재처리만으로 위 상태의 중단 복구가 완료되지는 않는다.

## 3. 환급 완료 판정

- 생성 오류 code는 환급 성공 증거가 아니다. FE는 오류만으로 완료 문구를 표시하지 않는다.
- B 즉시 보상은 A receipt의 사용자/견적/원거래/복구 거래를 검증한 뒤 REFUNDED로 전이해야 한다.
- A 복구 원장은 저장됐지만 B 상태 갱신이 실패한 경우, 같은 역분개를 재사용해 상태만 다시 맞춘다.
- 복구 실패/재시도 한도 초과의 사용자 표시, 관리자 처리 담당과 운영 알림을 정한다.

## B 합의 없이 진행하는 A 작업

충전 주문 생성/소유자 조회, 서버 가격·지급량 snapshot, 주문 키 중복 방지,
이후 토스 승인/결과 불명 조회와 지갑 지급 트랜잭션은 A 결제 모듈에서 진행한다.
이 작업은 B의 구매/생성 상태 머신을 변경하지 않는다.
정책 동의/보관 기간/판매 활성화와 실결제는 별도 확정·검증 대상이다.
