# 고객센터 접수와 관리자 잔여 등껍질 환불

기준: 2026-10-13 사용자 확정 방식. FE 코드·공유 OpenAPI·사용자 환경 파일·상품/권한·배포는 변경하지 않는다. 실제 문의 채널·처리 기한·시행일·운영자 지정은 별도 준비한다.

## 환불 정책

- 신청 기반이며 고객센터 문의를 운영자가 확인해 처리한다. 접수만으로 PG 취소하지 않는다.
- 충전 건별 **현재 유효한 잔여 유료분 전체**를 한 번에 환불한다. 정상 환불 완료 건을 새 요청키로 다시 환불할 수 없다.
- 금액 = **실제 원 결제액 × 남은 유료 등껍질 ÷ 최초 유료 지급량**. 정수 원 미만은 올림, 수수료 0. 서버가 저장한 결제/지급/원장으로 계산하며 관리자가 금액을 자유 입력하지 않는다.
- **남은 보너스는 회수하고 이미 사용한 보너스는 현금 공제하지 않는다.** 보너스는 현금 환불액의 분모/분자에 넣지 않는다.
- 5,000원에 유료 500·보너스 50을 지급했다면: 미사용→5,000원 및 550개 회수; 보너스만 50 사용→5,000원 및 유료 500개 회수; 보너스 50·유료 100 사용→4,000원 및 유료 400개 회수.
- 7일 이후도 잔여분을 환불한다. 일반 경로에 7일 실행 기한 gate를 두지 않아 문의를 뒤늦게 처리했다는 이유만으로 거절하지 않는다. 실제 문의 접수 시각과 서버 등록 시각을 구분해 기록한다.
- 관련 구매가 생성/반환 처리 중이면 먼저 정산한다. 완료된 구매 또는 원 거래 반환 receipt를 확인해야 한다. 반환이 끝난 지급분은 현재 잔량으로 계산하며 과거 사용 이력만으로 거절하지 않는다. B 완료 확인은 `WalletPurchaseSettlementPort`의 읽기 전용 adapter로 연결한다.
- 유료 만료/소멸분, 서비스 종료·미성년자·법정 예외·강제 회수/조정은 이 일반 경로로 처리하지 않는다. 가상계좌 환급 계좌 입력도 아직 제공하지 않는다.

## 접수와 권한

`ADMIN_OPERATIONS_ENABLED`, `ADMIN_RECOVERY_ENABLED`, `TOSS_REFUNDS_ENABLED` 및 지원 PG adapter가 필요하다. 기본값은 계속 비활성이다. 자동 환불 재개에는 `TOSS_OPERATIONS_ENABLED`도 필요하다. 실제 키는 사용하지 않고 synthetic provider와 분리 PostgreSQL로 검증한다.

현재 세션 사용자의 `admin_operator_grants.active/can_recover` 및 `users.status=ACTIVE`를 확인한다. 요청 헤더/클라이언트 ADMIN 역할은 권한 근거가 아니다. POST는 세션 쿠키와 CSRF가 필요하다. 읽기 권한 사용자는 조회/금액 확인만 가능하다. 접수/실행은 운영자·회원 행을 잠가 권한 철회와 예약이 경쟁하지 않게 한다. 실행이 승인되어 금융 의도가 영속 저장된 뒤의 서버 복구는 해당 의도를 이어가며 운영자 권한 철회가 이미 시작한 PG 작업을 취소시키지 않는다. 새 의도는 철회된 운영자가 만들 수 없다.

고객센터는 실제 신청자와 주문 소유자가 같은지 확인한다. 서버는 전달받은 고객 UUID와 주문 소유자를 다시 대조한다. `supportReference`는 원 문의를 찾는 개인정보 없는 식별번호(영문·숫자·하이픈·밑줄, 1~80자)다. 이메일 원문·이름·연락처·키·쿠키를 넣지 않는다. receivedAt은 실제 문의 접수 시각으로 입력하며 출처는 원 문의에 보관한다. 미래 시각이나 주문 생성 이전 시각은 거절한다. 서버 등록 시각은 수정할 수 없다.

## 운영 절차와 API

공통 prefix: `/api/v1`. 관리자 전용 OpenAPI: `backend/docs/openapi/admin-operations-v1.json`. 아래 UUID는 입력 필드의 의미이며 실제 주문/회원/응답 식별자를 사용한다.

1. 주문/본인 확인 후 `POST /admin/refund-cases`로 문의를 등록한다. `Idempotency-Key` 필수. 본문은 `orderId`, `customerUserId`, `supportReference`, ISO 8601 `receivedAt`. 같은 키/본문은 같은 caseId, 키 재사용으로 내용 변경은 409다. 주문당 한 접수 건이다. 현재는 접수 수정/취소·새 문의로 이전 반려 건 재실행을 제공하지 않는다.
2. `GET /admin/refund-cases/{caseId}/quote`에서 원 결제액 `originalAmount`, 실제 환불액 `amount`, 회수할 `paidShells/bonusShells`, `feeAmount=0`을 확인한다. 이 조회는 금액을 예약하지 않는다.
3. `POST /admin/refund-cases/{caseId}/execute`에 새 작업 요청키 및 quote의 `expectedAmount/expectedPaidShells/expectedBonusShells`를 전송한다. 서버 계산값과 일치하는지 재검사하며 다르면 409 `REFUND_QUOTE_CHANGED`다. 이전 PG 작업이 시작되지 않은 이 오류일 때만 새 금액을 확인해 새 의도로 제출한다. 같은 실행 키에 다른 case/금액/수량은 409 `IDEMPOTENCY_KEY_REUSED`다.
4. `GET /admin/refund-cases/{caseId}`로 결과를 확인한다. `refundId/state/amount/paidShells/bonusShells/completedAt`은 예약 전에는 일부 null이다. 실제 회수·환불 증거 및 감사와 함께 결과를 대조한다.

POST 실행은 대기 중 202, 환불/반려/검토 상태에서 200이다. HTTP 200만으로 환불 완료라고 안내하지 않는다.

| case state | 뜻과 대응 |
|---|---|
| RECEIVED | 접수만 저장. PG 호출/회수 없음. |
| RESERVED / IN_FLIGHT / RETRY | 회수 의도 저장·처리/재조회 중. 같은 case와 요청 의도로 확인한다. |
| REFUNDED | PG에서 지정 취소액이 확인되고 원장/주문/감사가 저장됨. amount만큼의 환불 완료. |
| REJECTED | 첫 시도에서 취소 없음이 검증돼 예약 재화를 원 지급분/만료일로 반환. 현금 환불 완료가 아님. |
| REVIEW_REQUIRED | 불명 소진/증거 불일치/외부 취소 등 확인 필요. 새 금액이나 DB 직접 수정으로 해결하지 않는다. |

일반 사용자는 기존 소유자 `GET /top-up-orders/{orderId}/refund`에서 실제 현금 반환액과 state/completedAt을 확인한다. **일반 사용자 환불 POST는 제거**했다. 고객센터 경로를 우회하지 않는다. 주문 조회의 `REFUND_PENDING`은 미완료/검토, `PARTIALLY_REFUNDED`는 원 결제액보다 적은 환불이 확인된 외부 상태다. DB 주문 lifecycle은 `REFUNDED`로 닫고 원 결제액/지급 스냅샷은 유지한다. refund state=REFUNDED는 해당 환불 의도의 amount 완료를 뜻하며 원 결제액 전부를 뜻하지 않는다. 공유 OpenAPI와 FE 생성 타입의 갱신은 FE 담당자가 함께 처리해야 한다.

## 트랜잭션·중복·복구

- 추가 migration `V202610131200`: 접수, 운영자 실행 키, 기존 환불의 접수/유료·보너스 회수 스냅샷. 최신 main의 B migration 이후로 배치해 이미 최신 B migration을 적용한 DB에도 순서대로 적용한다. 기존 공유 migration은 수정하지 않는다.
- 예약은 order→운영자/회원→case→wallet 순으로 잠근다. 실행 키·회수 원장/잔량·환불 의도·실행 감사가 한 DB 트랜잭션이다. 실패하면 모두 롤백해 PG 호출하지 않는다.
- 잠금을 푼 뒤 PG를 조회/취소한다. 동일 refundId의 PG 멱등키를 유지한다. 부분 취소는 원 결제액/키/주문/통화, 남은 PG 금액과 DONE 취소 이력의 합계·중복 거래키를 검증한다.
- timeout/프로세스 중단 상태에서는 영속 lease 만료 후 원 주문을 재조회한다. 이미 요청 금액만큼 취소됐으면 다시 취소하지 않고 완료한다. PG가 그대로 DONE이면 같은 의도/금액으로만 제한 재시도한다. 5회 소진은 검토 상태다.
- 오래된 lease 응답은 반영하지 않는다. 부분 취소가 내부 예약량/금액과 일치할 때만 완료하고 예상 밖 외부 부분 취소는 지갑 제한/검토로 전환한다. 전체 외부 취소로 부분 환불 예약을 완료시켜 잔여 결제액 차이를 숨기지 않는다.
- 최초 명확한 거절 또는 PG에 요청하기 전 미지원 수단이 검증되면 예약 유료/보너스만 원 지급분에 한 번 반환한다. 이전 불명 시도가 있으면 단순 거절로 반환하지 않는다. 가상계좌/부분 취소 불가 수단은 이 API에서 취소를 강행하지 않는다.
- PG 확인 후 환불/주문 완료와 최종 감사도 함께 저장한다. 감사 저장 실패는 완료 저장까지 롤백하지만 PG 취소 자체는 되돌릴 수 없으므로 원래 예약을 유지하고 조회 복구한다.
- B 미완료 구매를 확인하는 port는 읽기만 하며 A가 B 테이블을 직접 갱신하지 않는다. 신규 구매/보상/만료/환불은 같은 지갑 잠금으로 직렬화한다.

## 배포·남은 확인

활성 환불 작업이 있는 상태에서 구/신 worker를 혼합하지 않는다. 구버전은 잔여분 amount를 원 결제액 전체로 취소할 수 있으므로 **기능을 끄고 작업 정리·전 인스턴스 교체를 확인한 뒤 활성화**한다. DB에 새 칸을 추가했다는 이유만으로 이전 코드와 금융 동작이 호환되는 것은 아니다. 실제 서비스 환경/권한/키/상품/worker는 이번 작업에서 활성화하지 않는다.

운영자는 초기에는 Postman 등 관리 도구로 처리할 수 있다. 별도 관리자 화면은 필수가 아니다. 고객센터 접수 채널은 운영자 담당, 실제 세션/PG 연결과 사용 가능한 결제수단은 팀 검증이 필요하다. 토스 상점관리자에서만 취소하면 내부 회수와 분리될 수 있으므로 정상 환불은 이 서버 경로를 거친다.

최종 법률 원고·처리 기한·가상계좌/운영 live 지원·만료/종료/미성년자 예외, 실제 PG·OAuth·브라우저·OS 종료·부하·복원은 별도 검증/개발이다. 자동 테스트가 이 항목까지 확인한 것으로 표시하지 않는다.
