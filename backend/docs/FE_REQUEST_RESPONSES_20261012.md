# FE 10/12 요청에 대한 BE-A 답변 및 남은 결정

기준: 2026-10-12, 사용자 정책 정정과 PR #24·#25 병합 후 코드. 이 문서는 FE 요청서의 팀 답변 초안이다. 정책의 대외 원고, 실제 스테이징/PG 연결 성공을 뜻하지 않는다.

## 1. 사용자 확정 정책 (Q-21, Q-41, PAY-03)

- 현금 환불은 **고객센터에 신청한 건**을 처리한다. 신청이 없는데 기간이 지났다는 이유만으로 취소하지 않는다.
- 충전 주문 **생성 시각부터 7일 이내**, 그 주문의 **유료·보너스 지급분이 모두 한 번도 사용되지 않았고 미만료**이면 원 결제 금액을 **전액** 환불하고 보너스도 회수한다. 구매 실패로 등껍질이 다시 들어왔어도 사용 이력은 없어지지 않는다.
- **부분 환불은 제공하지 않는다.** 남은 유료분 비례 환불, 수수료 공제형 환불, 일부 사용분 환불 산식은 FE 문구·화면에 넣지 않는다. 법령상 취소·환불 권리와 예외는 PD/사업 담당자가 별도로 검토한다.
- 사용 시 만료가 빠른 지급분부터 차감하고, 만료가 같으면 보너스 먼저, 그것도 같으면 먼저 지급된 순이다. 보너스가 무조건 먼저인 정책은 아니다.
- 충전 완료 화면에서 이번 지급 유료/보너스 수량은 주문 `paidShellAmount`/`bonusShellAmount`, 현재 유료/보너스 잔액은 지갑 `paidBalance`/`bonusBalance`를 사용한다. 실제 지급 완료는 주문 `CREDITED`로 확인한다. 지갑 합계만으로 지급분별 유효기간 목록을 만들 수는 없다.

### Q-39 4: 로컬 진짜 모드 조건

- 충전 상품 6종과 수능운 상품은 시드에서 비활성이다. 분리한 로컬/스테이징 DB에서 담당자가 필요한 테스트 상품만 활성화해야 상품 목록·견적을 확인할 수 있다. 개발 DB나 운영 DB의 상품을 이 문서만 보고 일괄 변경하지 않는다.
- 충전 PG 연동에는 동일 상점의 테스트 클라이언트 키(FE)와 테스트 시크릿 키(BE), `TOSS_ADAPTER=api`가 필요하다. 현재 기본은 `disabled`다. `TOSS_RECOVERY_ENABLED`는 승인 결과 불명의 재조회 worker를 켜는 별도 설정이며 실제 환경에서 동작을 확인한 뒤 판단한다.
- 등껍질로 운세를 구매하려면 BE의 `WALLET_PURCHASES_ENABLED=true`와 결과 생성 adapter/관련 설정이 필요하다. 실패·중단 복구 worker는 `WALLET_RECOVERY_ENABLED`, `READING_GENERATION_RECOVERY_ENABLED`로 별도 제어된다. 준비된 환경에서 정책·DB·키·복구 경로를 함께 확인하고 활성화한다.
- 로컬 접속·로그인·CSRF·키 짝·상품·DB 마이그레이션·결제창·주문 `CREDITED`·원장/잔액·운세 결과는 각각 검증한다. 상품 목록이나 HTTP 200 하나만으로 연결 완료라고 판단하지 않는다. 실제 키·쿠키·토큰 값은 문서/채팅/로그에 기록하지 않는다.

## 3. 고객센터 접수의 서버 작업 (Q-41, R-06)

현재 `POST /api/v1/top-up-orders/{orderId}/refund`는 **주문 소유자 세션 + CSRF**로만 호출된다. 관리자 API는 환불 조회와 PG 상태 재확인은 가능하지만 **최초 현금 환불 신청/취소를 시작하는 명령은 없다**. 따라서 고객센터에서 신청을 받는다는 결정만으로 운영자가 환불을 실행할 수는 없다.

BE-A 후속 구현: 운영자 복구 권한, 주문·소유자 대조, 사유/요청키 영속 저장, 감사, 기존 전액 미사용 회수·PG 취소 경계 재사용을 갖춘 **관리자 접수 명령**을 추가해야 한다. PG 응답 불명은 기존 조회/재시도 경계로 이어가고, `REFUNDED`를 원장·주문·취소 증거와 함께 확인할 때만 완료라고 안내한다. 고객 세션 대리 사용이나 DB 직접 잔액 수정은 절차가 아니다.

실제 스테이징 준비도 별개다. 분리된 DB·고정 FE 주소·백엔드 주소·카카오 callback/프록시·같은 상점의 토스 테스트 키 짝·상품 활성화·필수 플래그를 B/A/FE가 함께 확인한 뒤 브라우저에서 로그인→충전→지급→구매를 검증한다. 테스트 키의 **시크릿은 BE에만**, FE에는 테스트 클라이언트 키만 둔다. 현재 기능 플래그와 상품은 기본 비활성이다. 배포 주소나 실제 연결 결과는 아직 확인하지 않았다.

## 5. 검증 기준과 범위

- 문서의 API/상태/필드는 저장소 코드 및 백엔드 전용 환불 OpenAPI와 대조한다. FE 코드와 공유 OpenAPI의 생성 타입 짝, 사용자 `.env`, 실제 상품/플래그, 관리자 권한은 이 문서 작업에서 변경하지 않는다. 공유 OpenAPI만 갱신하면 FE의 타입 동기화 CI가 실패함을 확인했다.
- 현금 환불은 주문 소유권 또는 운영자 권한, 요청키 중복, 지급분·원장·잔액, DB/PG 취소 경계를 함께 확인해야 한다. PG 대기 중 DB 잠금을 유지하지 않고 결과 불명은 재조회한다.
- 로컬 문서·생성 계약 검증은 실제 카카오/토스/FE 브라우저 통합 성공의 증거가 아니다.
